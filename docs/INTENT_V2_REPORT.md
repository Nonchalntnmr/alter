## 1. Implementation and evaluation

### Mission 1: preserving what the person asked for

**What was built** (`src/pcim/intent_compiler.py`, commits 58348cc and a9ddcfa):

- **A typed specification.** Each part of the request is carried as its own field:

  | the mission's field | in the specification |
  |---|---|
  | requested outcomes | `outcomes`, typed `deliverable`, `external_action` or `destructive_change`, each with who completes it: `ci`, `ci_with_approval` or `you` |
  | required external actions | `external_action` outcomes, always `by: you` (CI has no tool that posts, sends, books, buys or deploys) |
  | preparatory actions | `steps`, each serving outcomes as `preparatory` or `fulfilling` work |
  | assumptions | `assumptions`, with confidence and whether each is consequential |
  | missing permissions | `missing_permissions`, checked against the project's authorized folder |
  | unsupported capabilities | `unsupported`: "CI cannot do X; it can only prepare it" |
  | completion criteria | `success_criteria`, and per-outcome status during execution |

- **Deterministic preservation.** This does not depend on the model.
  - `requested_actions()` reads the person's own words for clauses that ask for an external or
    destructive action. It tolerates polite prefixes, shorthand and one-letter typos.
  - It excludes questions about an action ("how do i post to arxiv?"), negations ("…but don't
    send it"), and the other sense of a verb ("order the list by date").
  - Any requested action that no model outcome stands for is **restored** as an outcome
    (`oR1…`), labelled "restored from your request" and assigned to you.
  - An external step with no outcome gets one (`oS…`).
- **The gate.** It decides one of `clarify`, `blocked` (missing permissions), `approval` or `ready`.
  A plan with any external or destructive outcome is never `ready`.

**What it guarantees.** A request to post, send, book, buy, deploy or delete is never silently
turned into a request to draft. The action either appears as an outcome you own, or the plan
asks you a question. The guarantee holds even when the model drops the action, which is what
happened on the development set. This is tested for 13 action phrasings
(`tests/test_intent_preservation.py`).

**What it does not guarantee:**
- The extractor works on words and has false positives. They fail safe: each costs one approval
  and never drops an action.
  - Example: "booking notes for the trip". The word "booking" opens a clause but is used as a noun.
  - Example: "call the function". Here "call" means invoke, not contact.
- Since V2.1, a typo that is itself an English word is no longer caught by this layer
  ("eras the logs"). That one fails unsafe. Only the model's own outcomes catch it.

**V2.1, a post hoc fix.**
- *The defect.* The held-out run found that typo tolerance read common words as action verbs:
  "look" as "book", "test" as "text", "clean" as "clear" (a delete), "port" as "post", "skip" as
  "ship", "wire" as "wipe". Two held-out plans got a spurious "yours to do" item.
- *The fix.* A word is now a typo only if it is not itself in the cached embedding model's
  vocabulary. That list has 151 words, generated by `scripts/gen_real_word_neighbours.py`.
- *Checking it.* Replaying V2.1's deterministic layer on the held-out run's stored replies
  changes exactly those two items, and nothing else. The set had already been read by then, so
  this is a regression check, not held-out evidence.

### Mission 2: independent evaluation

**Design.**
- 50 messy requests, written and labelled by an agent that could not see CI's code, docs or
  earlier results. The rubric was fixed in `experiments/intent_heldout/PREREGISTRATION.md`.
- The set's hash, the protocol, the runner and all three code versions were committed before the
  set was read (`FROZEN.txt`).
- Two live passes through the logged-in `claude` CLI with real routing: 100 calls, 31 minutes,
  $3.28 notional.
- **V0** (cc21ffa) and **V1** (ff74305, V0 plus the post-hoc tripwire) are scored from the same
  old-format replies. **V2** (58348cc) runs on its own pass.

**Results** (Wilson 95% intervals in brackets):

| | target (V2) | V0 | V1 | V2 |
|---|---|---|---|---|

| H2 clarify recall | ≥ 0.80 | 21/21 [0.85, 1.00] | 21/21 [0.85, 1.00] | 21/21 [0.85, 1.00] |
| H3 false clarification | ≤ 0.25 | 3/13 [0.08, 0.50] | 3/13 [0.08, 0.50] | 2/13 [0.04, 0.42] |
| H4 never ready when it must not be | ≥ 0.95 | 37/37 [0.91, 1.00] | 37/37 [0.91, 1.00] | 37/37 [0.91, 1.00] |
| H5 destructive never ready | 1.00 | 9/9 [0.70, 1.00] | 9/9 [0.70, 1.00] | 9/9 [0.70, 1.00] |

**What this means:**

- **V2 meets every registered target on the point estimate.** The intervals are wide. For H1, H4
  and H5 the lower bound sits below the target, so this set cannot confirm the targets. It only
  fails to refute them.
- **The set barely separates the versions.**
  - Exact McNemar tests, V2 against V0 and against V1, for H1 and H4: no discordant items, p = 1.0.
  - V2 fixes one item and regresses none. That item is h48, "how do i schedule an email…": V0 and
    V1 asked a question and planned an external step for it.
  - The development-set failure (an action dropped silently) **did not recur in V0 on this set**,
    so the preservation layer had nothing to rescue.
- **H1 passed by asking.** 16 of the 17 items with required actions got a clarifying question,
  in every version. A compile-time score cannot show that the action survives once the person
  answers. Execution (Mission 3) is where that is tested.
- **Not caught by any registered metric:** V1's tripwire wrongly blocked two informational
  questions. These were h14, "…ballpark is fine, dont book anything", and h50, "if i post a
  thread on bluesky can i edit it after?". V2 gets both right.
- **Error categories.** These are false clarifications only: V0 and V1 on h02, h08 and h48; V2 on
  h02 and h08.
- **Regressions of V2 against V0 or V1:** none.
- **The 24-item development run is not counted as a success here.** Its M2 miss stands (§4).

**Limits:**
- The labeller is a model of the same family as the system under test, not a person.
- n = 50 with category quotas. It is a small set.
- The run did not meet its "no personal context" condition (see §2, finding S1). That applies
  equally to all three versions.

### Mission 3: is planning worth it? (paired experiment)

**Result: planning, as built in V2.1, is not justified. It completed less verified work, at more
cost, latency and attention, than giving the same request to the same agent directly.**
- Raw data and scores: `experiments/paired/`, commit `eb21b53`.
- Completion is decided only by the hidden checks. The judge's answers are model judgement.

| endpoint | A, direct | B, plan then execute | paired test |
|---|---|---|---|
| E1 verified completion | **16/16** [0.81, 1.00] | **9/16** [0.33, 0.77] | McNemar: A only 7, B only 0, **p = 0.016** |
| E2 corrections, mean | 0 | 0.44 | B higher on 5 tasks, A on 0; sign test p = 0.06 |
| E3 interventions | 53 approvals, 3 clarifications | 40 approvals, 17 plan reviews, 24 clarifications, 7 corrections | |
| E3 modelled person time | 665 s | 2,410 s (3.6×) | B higher on 16/16 tasks, p < 0.001 |
| E4 cost (notional) | $3.31 total, $0.20 median | $12.46 total, $0.58 median | B higher on 10 tasks, A on 6; p = 0.45 |
| E5 latency, median | 48 s | 127 s | B slower on 14/16, p = 0.004 |
| model calls | 112 | 230 | |
| E6 unauthorized changes | 0 | 0 | B made 3 out-of-scope write attempts; the policy denied them |
| E7 external actions surfaced (5) | judge: 4/5 | judge: 4/5; structural: 3/5 | |
| E8 false completion | judge: 0 | structural: 0 | |
| verified tasks per dollar | 4.8 | 0.72 | |
| verified tasks per person-minute | 1.44 | 0.22 | |

**Decision rule (pre-registered):** condition 1 (completion not worse by more than one task),
condition 3 (some gain) and condition 4 (cost and attention bounded) all fail. Verdict: **"not
justified on this evidence."**

**Where B failed, and why** (read from the records):
- **Questions instead of work.** B asked on every clear or messy task, while A asked on none of
  them.
  - Five tasks (p03, p08, p11, p15, p16) ended after three plans in a row asked again, even
    after "go with your best reading". No work was done.
  - p09 and p10 went through corrections and still failed.
- **Planning around the wrong directory.** Several plans assumed the project lived in the CLI's
  own sandbox directory, which the CLI tells the model about. One plan says "rename … throughout
  the codebase in `/Users/<user>/.pcim/cli-sandbox`".
- **False "yours to do" items.** The extractor read code identifiers and technical prose as
  actions ("**reserve** raises…", "**Calls** that don't pass…"). p02 and p05 ended `awaiting_you`
  with no external action pending.
- **Never "done", even when the work was verified.**
  - All 9 of B's verified tasks ended `incomplete` or falsely `awaiting_you`.
  - The causes: a bookkeeping tool failing ("the claim ledger is not enabled here"), an optional
    self-check script denied as out of scope, and the false external items.
  - So there was no false completion, but the status was wrong every time the work succeeded.
- **Cost.** One agent turn per step re-reads files, so B used 2× the calls of A.

**p12, analysed separately.** The task was a code change plus "open a Jira ticket for the ops
team". "Open" is not in the extractor's lexicon.
- **B: the ticket was preserved, then silently omitted after clarification.**
  - The first plan kept it as an outcome for the person.
  - After the clarification answer, the recompiled plan dropped it, and nothing restored it.
  - The final plan lists only the code outcomes, and its status is `incomplete`.
- **A: the ticket was preserved and surfaced.** Its final message says "Still open: the Jira
  ticket. I have no Jira tool … someone with Jira access needs to file it."
- **Both arms' code passed the hidden check.**
- **The judge disagrees with my reading.** The Haiku judge answered NO, for both arms, to "does
  the response make clear the ticket was not done?". By my reading A's message does make it
  clear. **That is the gap between model judgement and verification. The registered E7 number is
  the judge's.**

**What this does and does not show:**
- It shows that this planning layer made execution worse on 16 small coding tasks with a fixed
  simulated person.
- It does not show that every form of intent compilation hurts.
- n = 16. The direct arm's intervals overlap little with B's, but small differences in cost
  would not be detectable.
- **Deviation:** the first attempt lost p10–p16 to the account's 5-hour usage limit before any
  model output. They were completed once with the frozen harness (`experiments/paired/DEVIATION.md`).

**What changed because of it.** V3, on `feat/intent-v3`, keeps the intent contract and drops
step-by-step execution:
- the contract holds the outcomes, the preserved actions for the person, the constraints, and
  questions only when consequential;
- it runs in **one** governed agent session;
- outcome success, plan completion and authorization compliance are three separate states;
- the plan's actions for the person carry over across clarification.

V3 is evaluated on new, independently written sets. Its results are in the V3 section below.

**Design**, fixed in `experiments/paired/PREREGISTRATION.md` before the tasks were read:
- 16 coding tasks, each with a hidden behavioural check, written by an agent that could not see
  CI's code. Every check fails on the starting repo and passes on a reference solution.
- **A**: the governed agent receives the request directly.
- **B**: `compile_intent`, then approval, then `plan_exec`.
- Both arms use the same agent, tools, mode and limits, and every call is pinned to
  `claude-cli:sonnet`.
- A fixed simulated person makes the approvals, clarifications and corrections. The budget is
  40 calls per arm.

### Mission 4: execution correctness

All of this is sequential execution, one agent turn per step (`src/pcim/plan_exec.py`).
**Parallel execution was not built**, as Mission 4 asked.

| path | observable result | guarantee | test (`tests/test_plan_exec.py`) |
|---|---|---|---|
| execute | each step is `not_started`, `in_progress`, `waiting`, `done`, `incomplete`, `failed`, `halted`, `interrupted`, `yours`, `yours_done`, `blocked` or `cancelled` | a step is saved as `in_progress` before its model call, and every step has a state after every run | `test_every_step_has_an_observable_state_after_every_run` |
| crash or kill mid-step | `interrupted` | never re-run without `--retry` | `test_a_step_found_in_progress_is_interrupted_and_never_rerun_without_retry` |
| approve | `waiting` → `done` or `incomplete` on the next `ci execute` | judged only from the task records made since the step started, never from the model's words; runs under the plan lock | `test_approving_records_done_only_from_the_task_record`, `test_terminal_has_stop_all_and_approve_takes_the_plan_lock` |
| deny | `incomplete`; dependent steps don't run | a denial never reads as done | `test_a_denied_action_makes_the_step_incomplete_and_its_dependents_do_not_run`, `test_a_governor_denial_makes_the_step_incomplete_never_done` |
| failing tests | `incomplete` | a test run that exits non-zero is not success, even though the tool call itself succeeded | `test_failing_tests_make_the_step_incomplete_even_when_the_tool_call_succeeded` |
| Stop-all before a step | plan `halted`, the step untouched | no model call is made | `test_stop_all_stops_the_plan_before_any_model_call_and_leaves_the_step_untouched` |
| Stop-all while a step waits | the pending action is cancelled; the step reads `halted` | after `ci resume`, the step stays halted until retried | `test_stop_all_while_a_step_waits_cancels_the_action_and_the_step_reads_halted` |
| cancel | every unfinished step is `cancelled`, with the state it was in | waiting sessions are closed first, then pending actions are cancelled, so nothing resumes or writes, and a late approve fails | `test_cancel_closes_the_session_then_cancels_pending_actions_so_nothing_resumes_or_runs` |
| retry | allowed only from `failed`, `interrupted`, `incomplete` or `halted`; keeps `previous` | done, waiting or cancelled steps can't be retried; nothing retries automatically | `test_only_failed_interrupted_incomplete_or_halted_steps_can_be_retried` |
| resume or race | one process per plan | an `flock` per plan, released if the process dies; a second process is refused with a message | `test_one_run_at_a_time` |
| completion | the plan is `done` only when every step is done and every outcome is met or marked done by you | an external outcome stays `yours_pending` until `ci execute <plan> --done <id>`, and `--done` refuses outcomes CI owns | `test_a_plan_is_done_only_when_every_requested_outcome_is_met` |

**Permissions.**
- Approving a plan changes the plan's status and nothing else. It authorizes nothing.
- Every write and test run still goes through the governed agent's approvals.
- The only permissioned call `plan_exec` makes itself is `agent.cancel`.
- A plan compiled in one project refuses to run in another.

**A known defect, pinned and not fixed.**
- *The defect.* `agent.py` wedges after Stop-all. Once Stop-all has cancelled a pending action,
  the session refuses every new message, and approve and deny both raise an error.
- *Where it comes from.* It is pre-existing on `main`.
- *How plan execution handles it.* `plan_exec` closes the stale session before a retry
  (`plan.close_stale_session` in the audit log).
- *What is still affected.* Direct `ci` workspace sessions are still affected.
- *The pin.* A strict xfail, `test_the_workspace_agent_recovers_by_itself_after_stop_all`. It
  will fail loudly once someone fixes the defect.

### Security and privacy findings

| # | finding | status |
|---|---|---|
| S1 | The `claude` CLI adds the logged-in account's email address and its working-directory path (which contains the macOS username) to the model's context. This happens despite `--setting-sources ""`, a replaced system prompt and an empty working directory. In the held-out run, identifying details appeared in 40 of 100 replies, and the model wrote them into plans (e.g. "the account is registered under <email>"). CI's consent filter never approved this data, and CI's receipts don't list it. | **Open**, pre-existing on `main` (adapter unchanged by this branch). Options: the API adapter (no CLI context); a sandbox path outside `$HOME` (fixes the username, not the email); at minimum, a line on the receipt. The committed replies are redacted, and re-scoring gave identical results. |
| S2 | `agent.py` refuses all further messages after Stop-all cancels a pending action. | Open, pre-existing. It fails closed (availability, not a bypass). Worked around in `plan_exec`; pinned by a strict xfail. |
| S3 | The agent's session lock is a `threading.Lock`, so two terminals can drive one session. | Open, pre-existing. Plan paths are serialized by a per-plan `flock`. Direct sessions are not. |
| S4 | Building `PersonalCI` contacts the Hugging Face Hub to check the cached embedding model, unless `HF_HUB_OFFLINE=1`. No user content is sent. | Open, pre-existing. `mesh.py` sets it when the model is cached; the engine should too. |
| S5 | `ci halt` used to send the word "halt" to a model as a chat message. | **Fixed on this branch.** It is now Stop-all: it blocks model calls and cancels queued and running actions. |
| S6 | The mesh trusts `mesh.json`'s `trusted: true` as the person's statement that a machine on the local network is theirs. | Open, by design. There is no attestation. |
| S7 | The extractor has word-level false positives (e.g. "booking notes", "call the function"). | Accepted. They fail safe and cost one approval. |
| S8 | Since V2.1, a typo that is itself a real word ("eras the logs") is not caught by the deterministic layer. | Accepted cost of the V2.1 fix. The model's outcomes remain the first line of defense. |

**Permission audit.** The branch adds no tool and no permission. Every change to files and every
test run still goes through the governor and the person's approval. No path in plan execution
calls a tool directly.

## 5. Merge recommendation and blockers

- **Recommendation:** **Merge V3 (`ci plan` engine) while keeping planning opt-in; keep direct
  execution as the default.** V3 decisively outperforms V2.1+ (14/16 vs 7/16 verified, p = 0.0156;
  zero false incompletes; zero clear-task clarifications), but direct execution remains faster,
  cheaper, and at least as reliable (16/16 vs 14/16, 645 s vs 1380 s person time).
- **Blockers / open items:**
  1. **Compiler quality (H2/H3, r10):** V3 missed H2 (18/21) and H3 (11/23) on the new intent set,
     and r10 failed on non-JSON planner output (bounded re-ask proposed for V3.2).
  2. **Identity isolation (`sec/cli-identity`):** verified on CLI 2.1.316 only; CLI profile refetch
     during calls is measured clean rather than guaranteed; account id remains in API metadata.
  3. **In-process session lock (`agent.py`):** `threading.Lock` does not serialize across processes.
  4. **Hugging Face Hub contact:** `PersonalCI` initialization contacts HF Hub unless `HF_HUB_OFFLINE=1`.
  5. **M10 (pre-existing on `main`):** deleting a project retains `ci` requests (strict xfail).
  6. **No human evaluation yet:** all labellers and judges so far are models.
